# Working rules for this repository

These override default behavior. Follow them exactly.

1. **Ask before coding**: if anything is ambiguous or you have a design/scope question before
   writing code, use `AskUserQuestion` to ask first — don't guess, implement, and explain the
   guess afterward.

2. **Running tests/lint/commit/push**: don't run `npm test`, `npm run lint`, `git commit`, or
   `git push` unless the user explicitly asks for it, or it's genuinely necessary to verify the
   specific change you just made (e.g. confirming a bug fix actually fixes the bug). Implementing
   or fixing code does not by itself imply "and then test/lint/commit/push it."
   - When a test run is genuinely necessary, scope it narrowly — the specific test file or
     workspace package the change touches (e.g. `npx vitest run packages/<name>`) — never a full-suite run, unless the user explicitly asked for one.

3. **Investigation budget [IMPORTANT]**: if a task needs investigation (reading code, searching, tracing a
   bug), budget roughly 1,000 tokens of exploration for it. If you hit that limit and need more,
   stop and ask the user for permission before spending more.

4. **Claude session reference**: While creating commit and raising PR for GitHub, do not
   include Generated by Claude Code and Claude session references within the description.

5. **Commit Monitoring**: While raising commit, do not keep running the Claude, instead use monitoring to
   avoid spending tokens with a hook to identify when it is done and act on it.

6. **CHANGELOG.md entry style**: keep new `[Unreleased]` entries short — one or two lines,
   what changed from a reader's point of view, no file paths/function names/implementation
   rationale. That level of detail belongs in the commit message or PR description, not the
   changelog. This applies going forward only — don't rewrite past released versions' entries
   to match.

7. **README.md**: add/update the README.md from a user perspective rather than technical. For technical
   please create documents within docs/ folder.

## React conventions

Apply these when writing or changing package code. They follow `docs/development.md`.

8. **Peer dependencies**: `react` and `react-dom` are `peerDependencies` (`^18 || ^19`), never
   bundled. Don't import `react/cjs/*` or add React to `dependencies`. After changing build config,
   run `npm run check:packages` for the affected package.

9. **Components and hooks**:
   - Named exports only, no default exports.
   - Function components with `.jsx` for JSX; hooks are `use*` in `.js` and have their own tests.
   - Document props with a JSDoc `@typedef` and export it. No PropTypes, no TypeScript source.
   - Data comes in through props or callbacks. Never read global state or import from an app.

10. **Hooks rules**: follow the Rules of Hooks (`eslint-plugin-react-hooks`). Keep effect and memo
    dependency arrays complete, clean up subscriptions and timers, and don't use effects for values
    that can be derived during render.

11. **Styles**: CSS modules, shipped as one `style.css` that consumers import. No global CSS, no
    CSS-in-JS.

12. **Accessibility**: use semantic elements first, label every control, and keep `jsx-a11y`
    clean. Don't silence a11y lint rules without a comment saying why.

13. **Tests**: Vitest, jsdom, Testing Library and `vitest-axe`. Query by role and label, not test
    IDs or class names. Use `userEvent` for interactions. Every component gets an `axe` check,
    and tests must pass under StrictMode (the default via `vitest.setup.js`).

14. **Client-only by default**: don't use Server Component features. If an entry needs
    `"use client"`, make sure the build keeps the directive.

15. **Public API changes**: adding or removing an export, or changing a peer range, needs a
    short `[Unreleased]` changelog entry and an update to the package README.
